## [2.6.0] - 2026-09-17

### Добавлено

- **Тест правила (dry-run) в карточке настроек.** Новая панель оценивает гипотетический вызов
  инструмента против набора правил, который ворота держат загруженными в данный момент, и
  показывает вердикт, совпавшее правило (индекс и действие), размерности, которые оно ограничивает,
  и причину. Написан для вопроса, который YAML не может ответить осмотром: *что это на самом деле
  сделает?* — `args` — это ИЛИ по токенам, пустая размерность не ограничивает ничего, а `command`
  сопоставляет только разложенное **слово** команды, так что правдоподобно выглядящее правило
  может оказаться мёртвым на приходе.

  Отчёт нарочно разводит два ответа. **`verdict`** — результат политики всей цепочки (жёсткий
  запрет P0 → deny-ключевое слово → выдача P1 → правила P2 → ask P4 → permissive).
  **`ruleLayer`** — то, что цепочка `permissions` решает сама по себе, и лишь этот слой может
  назвать индекс правила: жёсткий запрет P0 или deny-ключевое слово пресета срабатывает *до*
  него и не оставляет правила после себя, так что панель так и говорит, вместо того чтобы
  приписывать постороннее правило. `matchedDimensions` также перечисляет размерности, которые
  совпавшее правило *ограничивает*, а не ту, что «вызвала» совпадение — размерности соединяются
  по И, так что единственная причина не может быть честно названа. `ruleCount` из 0 выводится
  как «загружено 0 правил, проверьте путь rulesFile», а не как «ничего не совпало».

- **`POST /api/dsh-perm-gate/dry-run`** — endpoint панели. **По построению только для чтения**: у
  него нет формы записи вовсе, неизвестные ключи тела отбрасываются, а не пересылаются, и он
  никогда не трогает правила, выдачи, состояние обучения и пространство имён настроек. Тест
  правила не должен уметь его менять. Оценивает против **живой** среды выполнения, а не новой,
  так что панель тестирует действующие правила — новая среда разрешила бы цепочку заново от
  другого корня и могла бы молча ответить о другом файле.

- **`src/dry-run.ts`** — `runDryRun` / `createDryRunRuntime`, общий вычислитель для CLI и маршрута,
  плюс `PermGateRuntime.explainRules` (отчёт слоя правил только для чтения) и
  `PermGateRuntime.explainCall` (чистое вычисление политики). `src/cli.ts` теперь тонкая обёртка
  над ним; его вывод не изменился на девяти повторных прогонах, проверен побайтово (включая
  случаи `--list`, без инструмента, битого JSON и пути записи).

### Исправлено

- **Панель теста правила сообщала `allow` для вызовов, которые правила отдают человеку.** Первая
  версия вычисляла через хост-ориентированный путь, который применяет сессионные слои — отступ
  пресета и деградацию ask при `approval: never`. У dry-run без сессии нет сессии, поэтому читатель
  политики отвечал «never», всякий `ask` деградировал в сквозной проход, и панель показывала
  **allow** ровно для тех правил, ради которых её открывают. Измерено на живом хосте:
  `shell ls -la` показывала `allow`, тогда как слой правил той же карточки говорил `ask`.

  `runDryRun` теперь сообщает вердикт **чистой политики** из `explainCall`: та же цепочка
  P0 → deny-ключевое слово → P1 → P2 → P4, с сессионными слоями состояния исключёнными, а не
  угаданными, и `reason`, который никогда не сжимается до голого `(default/passthrough)`.
  Хост-ориентированный вид остаётся доступен под `input.hostView`; CLI запрашивает его, так что
  его исторический вывод остаётся байт в байт идентичным (перепроверено: 9/9 случаев, SHA256 на
  случай).

- **Маршрут «только для чтения» не был read-only.** Он исполнял хост-ориентированный путь
  решения против живой среды, который дописывает аудиторские записи и фиксирует события решений —
  открытие панели теста правила писало в живую ленту решений. Чистый путь ничего не дописывает, и
  `test/dry-run.spec.ts` теперь утверждает, что вызов, который хост-путь *записал бы*, оставляет
  аудиторское зеркало на нуле.

## [2.5.0] - 2026-09-17

### Добавлено

- **Размерность правила `branch`** — сопоставление git-ветки / remote / защищённой ветки, так что
  правило наконец может сказать «никаких push в защищённую ветку», не зацепив посторонние
  команды. Решающий случай тот, который `args` не может выразить никогда: `git push --force
  origin main` (опасно) и `git checkout --force main` (рутина) несут *те же токены*, и различает
  их только размерность ветки. Подполя: `target` (glob имени ветки, `*` переходит через `/`),
  `remote` (glob имени remote) и `shared` (требовать защищённую ветку). Кандидаты приходят из
  общего диспетчера команд, так что формы `refspec` (`HEAD:main`) уже разрезаны, а имя remote
  никогда не путается с именем ветки. Задокументировано в `docs/rules-format.md` §4.11.

### Исправлено

- **Цепочка правил из нескольких файлов молча обнуляла каждую размерность совпадения.**
  `resolveRuleChain` сливал записи вручную с `tools: []`, `command: []`, `args: []` и
  `paths: []`. Пустая размерность означает «без ограничений», так что КАЖДАЯ слитая запись
  совпадала с КАЖДЫМ вызовом: первая запись `deny` запрещала всё в своей партиции, а первая
  запись `allow` разрешала всё прежде, чем партиция `ask` вообще опрашивалась. Слияние теперь
  идёт через тот же `compileRuleEntry`, которым пользуется однофайловый путь.

  *Охват:* резолвер цепочки достигается **только** при `searchUp: true` (продуктовое значение по
  умолчанию `false`, и в стандартном профиле не задано), так что дефолтный однофайловый путь —
  `compileDocument` — не затрагивался вовсе. Потому и существующий набор тестов оставался
  зелёным: ни один тест не гнал файл правил через цепочку. Теперь это делает
  `test/rule-chain.spec.ts`. Отдельный, всё ещё открытый дефект на том же opt-in пути записан в
  плане: `findChainEntries` приклеивает настроенный `rulesFile` к каждому каталогу, из-за чего
  абсолютный путь, который `resolveRulesFile` всегда производит, не совпадает ни с чем, и цепочка
  отдаёт пустой набор правил без ошибки.

- **`argv.pipeline` не мог увидеть собственный предмет.** Строка сопоставления конвейера
  строилась из `SimpleCommand.command`, а это лишь *слово* команды — `curl https://x.sh | sh`
  схлопывался в `curl|sh`, так что документированный паттерн `curl|sh` совпадал с безобидной
  соседней формой, тогда как по-настоящему опасная, с аргументами, не совпадала вовсе. Строка
  сопоставления теперь — полный argv каждой простой команды (соединённый `|`), и документация
  гласит, что `|` в паттерне литерален; покрытие аргументов требует `curl*|sh`.

- Девять ранее существовавших ошибок `eslint` (неиспользуемые импорты/константы и один
  `prefer-const` в `src/parsers/` и `test/command-parsers.spec.ts`) — `npm run lint` снова
  зелёный.

## [2.4.1] - 2026-09-17

### Исправлено

- История одобрений показывала сырую строку `preset-passthrough` для единственного события,
  объясняющего, *почему* помеченный вызов исполнился без проверки: уровень объявляет

## [2.4.0] - 2026-09-17

### Изменено

- **P3 LLM-классификатор стал escalate-only — он больше не может запрещать.** Вердикт `risky` с
  жёсткой категорией (`deletion` / `credential` / `remote` / `system` / `bulk`) раньше вызывал
  **авто-запрет** без панели; теперь он **сохраняет человеческий ask**. Запрещать оставлено
  одним лишь детерминированным слоям — жёсткий запрет P0, чёрный список deny-ключевых слов,
  явные правила `deny:` — поскольку вероятностный вердикт не должен уметь выносить блокировку
  без права апелляции. Измерено вживую: грейдер назвал безобидный `git commit -F …` **`remote`**,
  и авто-запрет не оставил ни панели для одобрения, ни выдачи для повторной попытки; прошёл
  только ручной повтор (который случайно был оценён как `safe`). Это также приводит код в
  соответствие с собственным правилом проекта: высокорисковые операции перехватываются
  **детерминированно, никогда по суждению LLM**.

### Добавлено

- Жёсткие категории риска сохраняют одно значимое отличие от `neutral`: они **никогда не
  выучиваемы**. Повторные человеческие одобрения не могут осадить вердикт
  `deletion`/`credential`/`remote`/`system`/`bulk` в авто-разрешение (раньше это было верно лишь
  как побочный эффект авто-запрета; теперь это явное свойство).

### Замечания о поведении

- При `approval: never` ask, который ворота не могут доставить, по-прежнему деградирует до
  сквозного прохода, так что помеченный классификатором вызов теперь **исполняется** там, где
  раньше он запрещался автоматически. Это прямое следствие «запрещать только детерминированно
  опасное, остальное вести переговоры»: переговоры требуют человека, а `never` означает, что его
  нет. Держите ворота на уровне, чей `approval` — `ask`, чтобы пометки до вас доходили.

## [2.3.0] - 2026-09-17

### Добавлено

- **Отступление больше не беззвучно.** Когда пресет разрешений сессии лежал вне `gatePresets`,
  ворота отступали и ничего не записывали — вызов инструмента выглядел в точности как вызов,
  который ворота осмотрели и разрешили. Теперь они записывают **одно** уведомление `stand-down`
  на переход (сессия, пресет) (никогда — на вызов), называя пресет, охват и тот факт, что жёсткий
  запрет P0 неактивен. Браузер рендерит его липкой полосой **GATE OFF** над полем ввода, а
  история одобрений показывает тег `Gate off`.
- Карточка настроек 自动审查 называет собственный пресетный охват ворот (`gatePresets`, по
  умолчанию `permissive` / `permissive-full`) и что происходит вне его, так что охват виден там,
  где уровень настраивается.

### Изменено

- **Задокументированное положение P0 ограничено по охвату, а не глобально.** Жёсткий запрет P0
  монотонен и не подлежит обсуждению *внутри пресетного охвата ворот*; между пресетами ворота
  отступают целиком — P0 включён — потому что собственной политикой выбранного уровня владеет
  эта сессия. Код всегда так себя вёл; `AGENTS.md` и четыре README утверждали обратное, из-за
  чего `danger-full-access` читался как «P0 всё ещё действует». Задайте `gatePresets: ['*']`,
  чтобы снова сделать P0 глобальным.

### Исправлено

- `DEFAULT_GATE_PRESETS` / `resolveGatePresets` переехали из `config.ts` (который импортирует
  schemastery) в свободный от зависимостей `preset.ts`, так что браузерная половина может
  рендерить охват, не утягивая node-only зависимость в клиентский бандл. `config.ts`
  реэкспортирует оба; существующие импорты не меняются.

## [2.2.0] - 2026-09-17

### Исправлено

- **Жёсткий запрет P0 пропускал все shell-инструменты, кроме четырёх.** `hardDenyReason`
  привязывал свою shell-инспекцию к локально определённой регулярке `/^(?:bash|pwsh|sh|cmd)$/`,
  которая **не** совпадает с `shell`, `terminal` или `powershell`. `shell` — основной
  shell-инструмент DSH, так что вся shell-проверка P0 — защита от перенаправления в защищённые
  пути — была **инертна для самой частой формы вызова**. Измерено, та же команда
  `echo x > /etc/passwd`: блокируется через `bash`, **разрешается** через `shell`. `engine.ts`
  теперь импортирует `SHELL_TOOLS` из `evaluate.ts`; ворота держали три копии того единственного
  факта, и лишь одна была полной.
- **`git push --delete` разбирался как обычный push.** `hasDelete` вычислялся в
  `analyzeSubcommand`, но читался только в ветке `branch`, так что `git push --delete origin
  main` проваливался в ветку простого push (`destructiveness: 4`), а запись `'push-delete': 5` в
  `DESTRUCTIVENESS_MAP` была мёртвыми данными.
- **Обнаружение защищённой ветки ложно срабатывало на любом имени со слешем.** Предикат
  отрезал всё до последнего `/`, так что `backup/main` и `feat/release` читались как защищённые.
  Теперь он отрезает только известные префиксы ref (`refs/heads/`, `refs/tags/`,
  `refs/remotes/<remote>/`). Направление важно: этот предикат питает **неотзываемый** P0, где
  при промахе ещё остаются за спиной слои ключевых слов / правил / LLM, тогда как ложное
  срабатывание блокирует легитимный рабочий процесс без всякого средства.

### Добавлено

- **Жёсткий запрет P0 на переписывание удалённой истории защищённой ветки.** `git push`, который
  принудительно перезаписывает или удаляет `main` / `master` / `production` / `release` /
  `stable`, отклоняется детерминированно, до любого вызова LLM. Существовавшая раньше защита —
  плоское, слепое к веткам, переопределяемое пространством имён ключевое слово
  `'push --force'`; это неоспоримый пол под ним.
  - **Escalate-only по построению, а не по конвенции**: хелпер возвращает `string | undefined`,
    которое вызывающий читает как deny / не решено. У него нет способа выразить allow, так что
    подключение его в P0 не может расширить то, что ворота позволяют.
  - Нарочно **не** покрыто (по-прежнему отдано слоям ключевых слов / правил / LLM): force-push в
    незащищённую ветку, `git push --force` без указания ветки и обычные push.
  - Первое продакшн-применение парсера команд (`command-dispatcher`, `command-semantics`,
    `parsers/git`, `parsers/shell-cmds`), на который до сих пор ссылался только его собственный
    тестовый файл.

### Тесты

- Новый набор `test/git-protected-push.spec.ts` (13 случаев): варианты парсера, предикат
  защищённой ветки в обе стороны, полное покрытие `SHELL_TOOLS`, четыре нарочно разрешённые
  формы и сегментация составных команд (`git status && git push --force origin main`).
- **Фальсифицировано**: откат каждого из трёх исправлений краснит ровно те случаи, что его
  охраняют (7 провалов суммарно), тогда как случаи намеренного разрешения остаются зелёными.
- Полный набор — **40 файлов / 459 случаев**; `typecheck` чист.

## [2.1.2] - 2026-09-15

### Добавлено

- **Патч глифа композера теперь едет с пакетом.** `scripts/patch-permission-glyph.mjs`
  внесён в белый список `files` и открыт как bin **`dsh-perm-gate-patch-glyph`**, так что
  повторное применение патча хостового бандла после обновления DSH больше не требует чекаута

  ```sh
  npx dsh-perm-gate-patch-glyph            # apply
  npx dsh-perm-gate-patch-glyph --check    # report only; exits 1 if the glyph is missing
  ```

  переписывать харнесс, в который установлен, без приглашения. (pnpm 10+ по умолчанию блокирует
  install-скрипты, если они не в белом списке, так что `postinstall` оказался бы ещё и
  обещанием, которое молча никогда не исполняется — хуже явной команды.)

### Изменено

- Скрипт теперь тестируем: его чистые части экспортированы (`sliceEntry`, `applyGlyphPatch`,
  `candidateBundles`, `findBundle`) и зафиксированы `test/glyph-patch.spec.ts` (11 случаев).
  Инвариант баланса скобок — тот, что важен: первая версия нарезщика сканировала от не той
  скобки и производила непарсируемый бандл, который ловила только собственная проверка
  `node --check` скрипта.
- `candidateBundles` вдобавок прощупывает хоистенный пер-профильный scope под `$DSH_HOME`, а CLI
  — no-op при импорте (главный блок исполняется, только когда файл — точка входа).

## [2.1.1] - 2026-09-15

### Добавлено

- **Сетевая поверхность исполнения (opt-in, по умолчанию выключена).** Локальный HTTP/CONNECT-прокси
  разбирает исходящий трафик *подпроцессов shell* по тому же файлу правил, плюс интерактивный путь
  одобрения для целей, которых не покрывает ни одно правило. Правило `deny` никогда не эскалируется —
  одобрение расширяет охват незарегистрированной цели, но не может отменить правило, говорящее
  «нет». Новая конфигурация: `networkEnabled` (по умолчанию `false`), `networkMode`,
  `networkUnlisted`, `networkUnattributed`, `networkBind`, `networkPort`, `networkNoProxy`,
  `networkInjectEnv`, `networkAskTimeoutMs`, `networkGrantTtlMs`. Диагностика на
  `GET /api/dsh-perm-gate/network`. Покрыто `test/network.spec.ts`, `test/proxy-errors.spec.ts`,
  `test/network-lifecycle.spec.ts` и `test/network-approval.spec.ts`.
- **Два уровня 自动审查.** `permissive` сохраняет встроенную файловую песочницу; `permissive-full`
  (подпись 自动审查（高权限）) сочетает то же поведение одобрения с `danger-full-access`. `sandbox`
  и `approval` пресета — независимые ручки, и их связка вынуждала к компромиссу: песочница
  `workspace-write` запрещает и именованные каналы, нужные дочернему процессу для старта, так что
  `git clone`, `sh.exe` MSYS2/Cygwin и ConPTY падали на единственном уровне, где ворота были
  активны. Оба уровня входят в `gatePresets` по умолчанию.
- **Расширение модели правил.** Шесть новых размерностей сопоставления (`params` / `absent` /
  `agents` / `when` / `argv` / `network`), цепочка правил из нескольких файлов с `searchUp` и
  запасным путём, а также обнаружение теней для недостижимых правил. Новая конфигурация:
  `searchUp`, `fallbackPath`, `badFilePolicy`, `maxChainLength`.
- **Горячая перезагрузка правил.** Наблюдатель chokidar перезагружает действующие файлы правил,
  с дебаунсом, LRU-вытеснением между рабочими пространствами и наблюдением файлов-кандидатов
  через глубочайшего существующего предка, так что файл правил, созданный посреди сессии,
  подхватывается. Новая конфигурация: `watch` (по умолчанию `true`), `watchDebounceMs`.

### Исправлено

- **Заблокированное соединение могло убить хост.** Когда прокси отвечал на CONNECT кодом 403,
  RST клиента производил `ECONNRESET` без приписанного обработчика, который эскалировал в
  необработанное событие `'error'` и завершал процесс DSH. Обработчики ошибок сокета теперь
  приписываются в момент соединения, с запасными `clientError` и реакцией на отказ обработчика
  позади них. Прокси политики не должен ронять свой хост.
- **Встроенные инструменты запрашивали одобрение.** Список авто-разрешений вёлся вручную, так
  что добавленные в DSH инструменты из него выпадали, и вызов только для чтения мог поднять
  запрос одобрения: `advanced_search`, `platform_search`, `free_search_test`,
  `context_compression_retrieve`, `memory_search_graph`, `memory_expand_graph_node`,
  `memory_import`, `memory_ruminate`, `memory_ruminate_cancel`, `memory_ruminate_status`.
- **Гонки жизненного цикла прокси.** `close()` теперь ожидает выполняющееся связывание вместо
  того чтобы наперегонки его обходить, ограничено, и параллельные вызовы `start()` делят одно
  связывание. DNS-запросы ограничены по времени, фаза установки соединения ограничена,
  параллельные соединения лимитированы, и бросающий исключение логгер больше не может
  эскалировать в падение. Разборка прокси регистрируется до ожидания связывания, так что ранний
  dispose не может утечь занятым портом или переписанным `process.env`.
- **`permissive-full` не имел иконки в селекторе композера.** Карта глифов селектора закрыта
  и, по собственному комментарию, не даёт ничего именам, сконфигурированным хостом, так что
  自动审查（高权限） отображался одним текстом, тогда как 自动审查 показывал щит+глаз.
  `scripts/patch-permission-glyph.mjs` добавляет недостающую запись в ту **хостовую** карту:
  идемпотентен, нарезка по глубине скобок, и сам прогоняет `node --check` по своему выводу и
  восстанавливает резервную копию при неудаче. Он патчит хостовый пакет, поэтому должен
  перезапускаться после каждого обновления DSH — переустановка плагина его **не** возвращает,
  поскольку `dsh plugin … add` пишет только собственный `node_modules` профиля. Задокументировано
  во всех четырёх руководствах по установке.

### Изменено

- `networkUnattributed` по умолчанию `allow`: трафик без shell-атрибуции — собственный клиент
  DSH (встроенный сетевой инструмент, LLM-транспорт), и проверять его значило бы позволить хосту
  заблокировать самого себя. Для более строгого поведения задайте `deny`.
- `networkUnlisted` по умолчанию `ask`.
- `DEFAULT_GATE_PRESETS` теперь `['permissive', 'permissive-full']`.

### Документировано

- **Сетевой прокси — кооперативный слой политики, а не граница принуждения.** Он видит только
  клиентов, читающих прокси-окружение. Измерено, не предположено: `curl` идёт через него, тогда
  как `node` `http`/`https`/`fetch` подключается напрямую, как и сырые сокеты, DNS, QUIC, цели с
  литеральным IP и дефолтные клиенты Java/.NET. Указано во всех четырёх README.

- **Сессионная уборка — цепочка авторизации теперь следует за жизненным циклом сессии.** При
  старте плагина и каждый час ворота читают хранилище рабочих пространств DSH
  (`$DSH_HOME/storages/workspace.json`, только чтение) и классифицируют каждую сессию, по
  которой держат данные ворот. Сессии, которые DSH архивировал (`global.archivedSessionIds`) или
  вообще больше не отслеживает, теряют свои события решений из
  `$DSH_HOME/perm-gate/events.jsonl` (атомарная перезапись tmp+rename, только если что-то
  удаляется), а их снимки до изменения удаляются из `$DSH_HOME/perm-gate/snapshots/`. Живые
  сессии не затрагиваются; неатрибутируемые строки (пустой идентификатор сессии, неразбираемая
  строка/файл) никогда не удаляются; каждый сбой ввода-вывода — fail-open (проход пропускается и
  повторяется через час); часовой таймер `unref`'нут и утилизируется вместе с плагином. Новая
  конфигурация: `sessionSweep` (по умолчанию `true`), `workspaceStoreFile` (по умолчанию
  `<dshHome>/storages/workspace.json`). Учтите, что восстановление архивированной сессии не
  возвращает её вычищенную историю. Покрыто `test/session-sweep.spec.ts` (13 юнит-случаев) и
  `test/session-sweep-apply.spec.ts` (сквозная проводка).

- **Ворота отступали на каждом вызове под DSH 0.1.2, из-за чего страница Approvals пустовала.**

- Ушедший уровень разрешений **Auto** больше не повторяется в `cordis.patch.yml`. Патч бандла
  DSH заменяет всю карту `permission.config.presets`, так что файл должен был нести каждый
  уровень, которому полагалось выжить — включая `auto`, который вносил `dsh-auto-mode`. Тот
  плагин удалён: его ручки были идентичны `workspace-write`, его описание «автоматический обзор /
  одноразовое одобрение» лишилось реализации вместе с ним, и эти ворота на том уровне неактивны
  (`gatePresets` по умолчанию `['permissive']`). Селектор теперь предлагает три встроенных
  (`read-only` / `workspace-write` / `danger-full-access`, повторённых из
  `@deepseek-ai/dsh-base/cordis.patch.yml`) плюс `permissive` этого плагина.
- `test/patch-presets.spec.ts` фиксирует в точности тот набор ключей, так что встроенный уровень
  больше не может быть уронен (или ушедший воскрешён) без провала набора тестов.

### Изменено

- **Поддержка двух версий DSH (0.1.0-rc.7 … 0.1.2-rc.1).** Один артефакт теперь покрывает
  `dsh-v0.1.1-rc.2` и `dsh-v0.1.2-rc.1` без проверки версии. `effectivePolicy` — **приватный**
  метод сервиса пользовательского одобрения в обеих версиях, так что он читается через пробу
  `typeof`, а проба, бросающая исключение или отсутствующая, теперь деградирует до «политика
  неизвестна» (ask остаётся) вместо провала пути решения. Регистрация настроек сохраняет
  `ctx.settings.register`, существующий во всех поддерживаемых версиях. `dsh.client.inject`
  больше не называет `@deepseek-ai/dsh-client-runtime` (удалён в 0.1.2) ни
  `@deepseek-ai/dsh-client-ui-slots` (не динамическая клиентская строка ни в одной версии);
  теперь он перечисляет реальные клиентские строки, в которые рендерит. В README добавлены
  `engines.dsh` и таблица совместимости версий.
- Ворота **активны только на уровнях разрешений, перечисленных в `gatePresets`** (по умолчанию
  `['permissive']` — уровень, добавляемый этим плагином). На любом другом уровне — Read Only,
  Workspace Write, Auto, Full access, `custom` — поток решений вовсе не запускается: ни allow,
  ни ask, ни deny, ни жёсткого запрета P0, ни вето ключевых слов, ни аудиторского события.
  `gatePresets: ['*']` снова делает ворота глобальными (жёсткий запрет включён); встраивание,
  не передающее охват, сохраняет прежнее поведение.
- `llmAssist` теперь использует протокол категорий риска (надмножество прежних вердиктов
  allow/deny/ask); `classifier.ts` делит один OpenAI-совместимый транспорт (`chatCompletion`) с
  грейдером риска. Жёсткие категории риска (`deletion` / `credential` / `remote` / `system` /
  `bulk`) теперь **запрещают автоматически** вместо маршрутизации человеку — операция явно
  опасна, и попап не нужен; лишь `risky:neutral` (неопределённо) по-прежнему доходит до
  человеческого шва.
- Инструменты `write` / `edit` получили **зависящий от пути дефолт**: записи внутри рабочего
  пространства следуют настроенному `defaultAction` (обычно `allow`); записи в пути вне рабочего
  пространства сессии эскалируются в `ask`, чтобы содержимое можно было проверить. LLM-классификатор
  затем может авто-разрешить безопасное содержимое или авто-запретить вредоносное, так что лишь
  по-настоящему неопределённые операции дают попап.

### Исправлено

- **«safe» у `llmAssist` теперь действительно разрешает автоматически, а не только
  записывается.** Слушатель `tools/pre-execute` возвращал `ask` немедленно и оценивал вызов в
  фоне, но ask, вручённый хосту, уже в пути к ответчикам одобрения, и DSH не даёт API отозвать
  его (собственный `signal` запроса может лишь закрыть его как `cancelled`). Панель поэтому всё
  равно появлялась, и человеку приходилось кликать, тогда как лента показывала авто-разрешение
  `safe` — а жёсткорисковый `auto-deny` вообще не доходил до хоста. Слушатель теперь ждёт
  `refineAsk` **до** возврата решения (`makePreExecuteListener`): `safe` делегирует через
  `next()` без панели, жёсткая категория запрещает автоматически, и лишь `risky:neutral` /
  `unresolved` / сбой грейдера оставляют человеческий ask (fail-closed). Ожидание ограничено
  `riskTimeoutMs` (по умолчанию 20 с), и уже отменённый вызов пропускает оценку.
- **Слой shell-паттернов записи никогда не работал для основного shell-инструмента DSH.**
  `SHELL_TOOLS` перечислял `bash` / `pwsh` / `sh` / `cmd` / `powershell`, но не **`shell`**
  (собственное имя инструмента DSH) и не `terminal`, так что `git push`, `chmod`, `tee`,
  перенаправления и всякий прочий паттерн записи проваливались в `defaultAction` вместо
  эскалации в `ask`. Список теперь `shell` / `terminal` / `bash` / `pwsh` / `sh` / `cmd` /
  `powershell`, а дублирующая копия в `learning.ts` удалена (единый источник в `evaluate.ts`,
  чтобы путь решения и отпечаток обучения снова не разошлись).
- **Обнаружение перенаправлений и `tee` было слишком узким.** Совпадало лишь `>>`, так что
  `echo x > /tmp/out.txt` и голый `tee /tmp/log.txt` считались только для чтения. `> f` / `>> f`
  / `>f` теперь эскалируют, тогда как stderr-идиомы, которыми пользуется команда только для
  чтения (`2>&1`, `>&2`, `2>/dev/null`, `1>&2`), остаются только для чтения; `curl` / `wget`
  эскалируют лишь когда пишут файл (`-o` / `-O` / `>`).
- **`decideRules` игнорировал `args.command`.** Она читала лишь производный `ctx.commandText`,
  так что любой вызывающий, строящий контекст вручную (тесты, встраиватели), молча терял
  инспекцию команды. Теперь она возвращается к `args.command`, как `PermGateRuntime.ctxFor`.
- **Ворота перебивали выбранный пользователем уровень разрешений.** Они владеют независимым
  уровнем одобрения, но действовали в *каждом* пресете: всякое пересечение становилось `ask`,
  `dsh-tools` пересылал его в шов одобрения DSH, а под пресетом `danger-full-access`
  (`approval: never`) тот шов возвращает `rejected` **до того, как любой ответчик запустится** —
  панель никогда не рендерилась, и всякий не-только-чтение вызов падал с вводящим в заблуждение
  `the user rejected tool "..."`. Его слои жёсткого запрета и ключевых слов тоже игнорировали
  уровень, так что `danger-full-access` («полный доступ без запросов одобрения») молча сужался.
  Весь набор ворот теперь ограничен `gatePresets`; вне их ворота инертны и ничего не записывают.
  Внутри активного уровня `ask` всё же деградирует до сквозного прохода, когда действующая
  политика одобрения сессии — `never`, так что безответный ask никогда не становится отказом.
- **Поиск только для чтения и сессионные инструменты вызывали вопрос.** `web_search` и
  `modlens_read_image` — запросы только для чтения, а `todo_write` / `render_ui` /
  `validate_dsh_ui` / `ask_user_question` / `exit_plan_mode` / `ralph` / `workflow` — сессионное
  состояние или делегирование, но ни один не был в классификации авто-разрешения, так что каждый
  поднимал `ask` (попап `no rule matched; default action`). Теперь они разрешаются автоматически,
  а новый список конфигурации `autoAllowTools` расширяет классификацию на сторонние
  только-читающие инструменты. Жёсткий запрет P0 и слой ключевых слов по-прежнему работают
  первыми, так что список не может никогда расширить полномочия.
- **`write` / `edit` в пути вне рабочего пространства молча проходили насквозь.** Вызов, пишущий
  в `~/.bashrc` или файлы другого диска, получал настроенный `defaultAction` (обычно `allow`) и
  исполнялся без проверки. Зависящее от пути переопределение теперь применяется к
  write/edit-инструментам, когда ни одно правило не совпало: записи внутри рабочего пространства
  следуют настроенному `defaultAction`, но любой целевой путь вне рабочего пространства сессии
  эскалируется в `ask`, чтобы содержимое можно было проверить — вредоносное содержимое
  запрещается; безобидные дополнения авто-разрешаются при включённом `llmAssist`. Явные правила
  deny по-прежнему побеждают независимо от охвата пути, а явные правила allow могут дать доступ
  к внутренним путям, но никогда не обходят проверку внешних.
- **Обнаружение учётных данных P0 сканировало тела документов**, так что запись или правка
  любого файла, лишь *упоминавшего* токен, приватный ключ или `credentials.yaml`, жёстко
  запрещалась. Теперь сканируются только аргументы, описывающие операцию (`command`,
  `file_path`, …), в согласии с существующим правилом слоя ключевых слов: текст файла — не
  операция.
- **`$DSH_HOME/perm-gate/rules.yml` никогда не загружался.** У `rulesFile` не было значения по
  умолчанию, так что запись профиля без `config` оставляла ворота с пустым набором правил и
  `defaultAction: ask` — `defaultAction: allow` пользователя и его правила `allow:` молча
  игнорировались. `rulesFile` теперь по умолчанию `<dataDir>/rules.yml` (как `eventsFile` /
  `learningFile`), и зеркало белого списка в карточке настроек действительно пишет туда.
- **`format` накладывал вето на командлет PowerShell `Format-Table`.** Дефис — не граница слова
  для идентификатора команды, так что чёрный список совпадал с `Format-Table` / `Format-List`.
  Края ключевых слов теперь совпадают по символам идентификатора (`[A-Za-z0-9_-]`), так что
  `format C: /q` по-прежнему ловится, а `Format-Table` и `mkfs.ext4` ведут себя как прежде.
- **Всякий читающий запрос требовал ручного одобрения.** `read` / `read_image` / `grep` / `glob`
  / `ls` / `lsp` — операции чтения в пределах рабочего пространства, которые ничего не могут
  изменить (жёсткий запрет P0 по-прежнему блокирует чтения чувствительных путей вне корня
  рабочего пространства). Теперь они разрешаются автоматически. То же верно для всех внутренних
  координационных инструментов DSH (`agent_teams_*`, `conversation_search`, `memory_*`,
  `get_goal` / `update_goal` / `create_goal`, `taskboard_*`, `job_*`, `list_agents` /
  `interrupt_agent` / `send_message`, `subagent` / `subagent_fork` / `terminal` / `skill`).

- **Вкладка Approvals не разрешала идентификатор сессии**, так что она ничего не перечисляла,
  пока панель снапшотов показывала глобальный инвентарь. Занимающий `conversation.view` получает
  стандартные пропсы на верхнем уровне (`sessionId` / `useSessions`) — форму, которую потребляет
  `ConversationRoot`, — а не под `slotsProps`; вид и полоса уведомления теперь прощупывают
  верхний уровень, вложенную форму и хук списка сессий.
- **События записывались с пустым идентификатором сессии**, так что вкладка Approvals
  (фильтрующая по текущей сессии) не показывала ничего, хотя `events.jsonl` наполнялся. `ToolExecution`
  DSH несёт сессию на `agent.session.id` (cwd рабочего пространства на
  `agent.session.header.cwd`), а не на `exec.sessionId` / `exec.cwd`; оба теперь читаются с
  агента, когда прямые поля отсутствуют.
- **Страница обзора была молча мертва при установке по умолчанию**: при записи профиля без
  `config` `dshHome` был пуст, так что каталог данных был `undefined`, а журнал событий никогда
  не конструировался — ни `events.jsonl`, ни снапшотов, ни сохранённого обучения, и 404 на
  `GET /api/dsh-perm-gate/events`. `dshHome` теперь разрешается в явное значение, иначе
  `$DSH_HOME`, иначе `~/.dsh`, так что `<dshHome>/perm-gate/{events.jsonl,learning.json,snapshots/}`
  всегда записывается.
- Сопоставление deny-ключевых слов больше не накладывает вето на ключевое слово, лишь
  встречающееся внутри более длинного идентификатора, а аргументы тел документов (`content`,
  `new_string`, `old_string`, `text`, …) вообще больше не сканируются — текст файла не есть
  операция. Сопоставление теперь учитывает границы слов, так что ключевые слова с пунктуационными
  краями и CJK продолжают работать, а пробельные символы схлопываются, так что команда, записанная
  лишними пробелами, по-прежнему ловится.


### Добавлено
- **Уровень Permissive** — независимый режим одобрения наравне с read-only / workspace-write /
  full-access / whitelist. Единственный фронтовой переключатель (`permissive`) плюс комбинируемые
  серверные стратегии (`trustAutoAllow` / `alwaysConfirm` / `llmAssist`); жёсткий запрет P0
  остаётся монотонным.
- Аудиторские источники решений `classifier` / `permissive`; опциональный впрыскиваемый хук
  `classify` для `llmAssist` (fail-closed при `ask`/отсутствии).
- **Браузерный клиент** — страница `settings.plugins.tab` («Уровень одобрения Permissive»)
  рендерится в Настройки → Плагины: один переключатель (`permissive`) + три тумблера серверных
  `permissiveStrategies`. Хост читает пространство имён вживую, так что правки применяются к
  следующему вызову инструмента без перезапуска.
- Флаг CLI `--permissive` и перmissive-сводка в `--list`.
- **Настоящая LLM для llmAssist** — настраиваемый OpenAI-совместимый классификатор
  (`classifierEndpoint` / `classifierModel`), призываемый автоматически решать `ask` и
  fail-closed к человеческому шву.
- **Миграция белого списка** — `approveAllowEverywhere` сохраняет слово команды в белый список
  `allow` файла правил и перезагружает; `approveRepeat` чеканит ограниченную сессионную выдачу.
  Оба стоят за двумя расширенными кнопками allow панели always-confirm.
- **Руководства по установке на четырёх языках** — `INSTALL.md` / `INSTALL.zh.md` /
  `INSTALL.ja.md` / `INSTALL.ko.md` с установкой, обновлением, миграцией с раздельных плагинов,
  проверкой и устранением неполадок; каждое README получило ссылки переключения языка, заметку о
  совместимости `ja` / `ko` (официальный `LOCALE_IDS` DSH — `["zh", "en"]`) и ссылку на версию.
- README.ja / README.ko расширены до полных зеркал английского источника истины (таблица цепочки
  P0–P4, зачем/возможности, формат файла правил, уровень Permissive, CLI).
